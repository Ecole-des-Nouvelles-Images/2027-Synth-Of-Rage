Unity Terminology & Naming Conventions

Foreword

This document is a tentative to standardize the naming of any assets within an Unity project. The objective is to keep a consistency across all objects, structures and codebases, like if a single person worked and named everything according to it's own logic.

This aims to improve the efficiency within a team/project, help external contributors to familiarize faster with the project structures and optimize Unity Search indexer for faster queries, while remaining informative and act as an accessible cheat-sheet.

Disclaimer

This convention is made from experience and personal taste and is merely a guidance rather than enforced rules. You shouldn't feel locked behind them or be confused while using them.

Anyone is invited to question these rules and discuss it among your colleagues to find rules more adapted, more convenient or more strict, depending your day-to-day cases and project type/size.

The key thing to retain is to share various rules between team members across a project, apply them consistently, and keep them end-to-end !

Reference

This document is heavily inspired from the Unity Style Guide made by justinwasilenko and also tries to mimic the Unreal Engine Naming Convention when applicable.

Introduction

Terminology

Unity, like all game engines, have unique concepts/systems with it's own terms. Below you'll find the most common terminology to avoid any major confusions and get some similarities compared to other engines.

Assets

 Assets are the "physical" files, all the resources that are created and/or added to a project and used to construct a game. They come in several types, the most common being 3D models, 2D textures or sprites, audio clips, scripts, etc.
Inside a project, nearly every file should be treated as an asset.

Game Objects

 In Unity, everything depends on a GameObject.
GameObjects are often rendered, allowing you and your players to see them.
They can be a character, a terrain, a light, etc…

GameObjects can also be invisible, being a empty object where scripts are attached, executing game logic or representing an area to trigger events, or being a position where a character will spawn.

Scenes

 Often called maps or levels, a Scene contains a collection of GameObjects and Prefabs.

Scenes are versatile: you can either design a whole world into a single scene or create several levels throughout smaller ones.
They can also exist side by side. Thanks to this feature, you can split a level into multiple sections that can be added on top of each other and unloaded as needed.

Prefabs

 Unity allows you to create and store a single or a set of GameObjects, along with all their attached components, property values, and hierarchy of child objects.
When saved, you get a reusable asset called a Prefab.

Prefabs make designing objects and entities easier and facilitate the construction of more complex things by nesting Prefabs together.

Serialization

 This is, basically, the process Unity undergoes to save and reconstruct your Scenes and Assets. The serialization also creates the link between the codebase data structures and GameObjects.

Game developers can use the Serialization API to save objects and data that Unity would normally fly over. This allow manipulations of data within the editor and external saves, among other things.
For more information, see Unity's documentation on Serializable.

Render Pipeline
The Scriptable Render Pipeline or SRP (rarely RP) is the backbone of Unity's render system.
With SRP, game developers have access to the render pipeline themselves.
They can write a new SRP or customize an existing one, deeply influencing how a game might looks and how objects are rendered.

At the time of writing (up to editor version 6000.3.x), Unity provides two production-ready yet customizable versions of the SRP:
  • Universal Render Pipeline or URP → Lightweight and ideal for all types of gameplay across a wide spectrum of devices, including low-end mobile or virtual reality headset for XR projects.
  • High-Definition Render Pipeline or HDRP → Specialized pipeline for high-end devices and larger projects, using high-resolution graphics like raytracing or for intensive gameplay simulations.
For more information, see Unity's documentation on the SRP.

Note

A exhaustive and description glossary is made available by Unity → Unity Glossary

A less descriptive terminology, used mainly for writing and format Unity technical documentation is available there → Unity Docs Style

Naming Style and Cases

There are a few different ways you can name things. You should always stick to a pre-existing naming style, if one is present. Otherwise, you should select one yourself or as a team and keep it, end-to-end.

Here are some common casing types:

PascalCase

 Capitalize every word and remove all spaces.
→ e.g. 
GameObject
,  
StyleGuide
,  
ASeriesOfWords

camelCase

 The first letter is always lowercase but every following word starts with uppercase.
→ e.g. 
gameObject
,  
styleGuide
,  
aSerieOfWords

snake_case

 Words are always lowercase and are separated by an underscore.
→ e.g. 
game_object
,  
style_guide
,  
a_serie_of_words

Pascal_Snake_Case

 A fusion between the PascalCase and the snake_case.
Inherit the capitalization of all words but they are separated by an underscore.
→ e.g. 
Game_Object
,  
Style_Guide
,  
A_Serie_Of_Words

Warning

Some contexts or queries may be case-sensitive, meaning that naming will be important in how things are compared or evaluated. → e.g. GameObject ≠ gameobject in a case-sensitive context.

Scene Hierarchy

Scene “folders”

Use empty GameObjects with regular naming to make “folders” within the scene then parent sub-objects to them. Don't use affixes or names with symbols like –--Camera--- or [Debug].

Script-only GameObjects

When a GameObject serves only as a container for scripts. It should have the @ prefix. This should be applied regardless the parenting level of the object (parent/child).

Dynamic root

When instantiating objects at runtime, make sure to parent them under the _Dynamic GameObject (or one of it's children). This will make easier to inspecting the hierarchy when debugging.

Project Hierarchy

Top-Level folder

If your project is named GenericShooter, you should find a top-level folder Assets/GenericShooter/. There are multiple benefits, as suggested by justinwasilenko:

  • No global assets

    This encourages a strict structure layout and avoid re-organizing several assets across different root/parent folders, and breaking potential links.

  • Reduce Migration Conflicts

    It is common for a team to copy and pull assets from one project to another. By placing all project-related assets into a named top-level folder, it avoid potential naming conflicts or duplicates from external source, and also, facilitate custom packages exportations between Unity's versions in case of migration.

  • 3rd Party content, DLC or Patches more maintainable

    Unity samples, third-party content or templates are not guaranteed to conform to the top-level folder rule. Even if that was the case, structures can change between version upgrades. Separating them from the project's files ensure the project will never break when importing external content.

Developer folders

Developer folders are a convenient way to allow experimental or test assets while keeping them organized and aside the project hierarchy.

Under a common _Dev folder, each team member can own a named folder to put any temporary assets. Theses folders can also be added to source control and tracked, if required.

Another benefit of developer folders reside in the exclusion of WIP assets from the final product. By doing so, designers won't misuse any assets, avoid reworking whole chunks every time an asset changes.

Only when assets are finalized (and/or approved), they are “promoted” inside the product top-level folder.

Redundant and shared folders

Being strict on the on the naming system enable to let go of many redundant folders like Meshes, Textures or Materials. All assets being prefixed, they instantly hint their type at glance and are shorter to type when searching for them. As also said previously, the Unity Search indexer will also save time when resolving queries.

When assets do not belong to any subset of assets or are reused across the whole project, they should be located inside a MaterialLibrary folder. This is useful for generic and common materials but this folder it also intended for utility textures, shader functions or sub-graphs, test models, etc…

Alternatively, assets that are shared or relative to a subset of object (Characters, Audio, Architecture, etc…) should fall within a _Common folder, specific to that scope. → e.g. Character/_Common/Animations/ or Lighting/_Common/GlobalSettings.asset

Scenes folder and underscore prefix

Scenes are very special assets. They need to be easily available for developers in order to be integrated into a build. Designers must also not confuse them when working on them.

For that matter, all scene assets must be located within a single folder _Scenes.

This folder should move back up the hierarchy and always come first to avoid any confusion with other folders, hence the underscore _ prefix.

It might be handy to isolate other special folders with the _ prefix. This is notably the case for _Common folders and the _Dev root folder .

Asset Naming Convention

All assets must be strictly named according to the following naming pattern:

Prefix_BaseAssetName_Variant_Suffix

This naming convention must be applied both when naming GameObjects inside a scene and for the naming of assets files within the project hierarchy.

Correctly naming objects in scenes gives their corresponding name when making a Prefab and inversely, adding a correctly named Prefab within a scene keep its hierarchy clean and coherent.

In this pattern :

Prefix
Prefixes indicate the type of an asset. They often are the acronym of the type's full denomination. Go to affixes tables for more.
⚠ Warning
Native and/or custom types may have the same acronym (e.g. AudioClips vs AnimationController). A conflict occur as they would both use the AC_ prefix.
In this convention, the necessary should be done to keep prefixes unique, although this might come at the cost of exhaustiveness.

Other conventions may allow this discrepancy for the sake of simplicity.
Variants
An object can have multiple Variants. They are logical groups representing subset of the base asset like different sizes, shapes, species, age/era, rarity, etc… (e.g. SM_Cat_MaineCoon, SM_Cat_Persian, SM_Cat_Siamese, ...).
Variants can also be chained (e.g. SK_Player_Skin_Legendary_SkinName).

In case of generic subsets, variants should be named incrementally (e.g SM_Rock_Volcanic_01, SM_Rock_Volcanic_02, ...). You can also use letters on limited subsets (e.g. SM_Wall_A, SM_Wall_B, ...). Favor consistency and ideally numbers over letters.
Suffix Suffixes are similar to variants and are use to describe a set of similar assets.
They flags more informations about an asset's type.

The more flagrant usage of suffixes is with Texture assets.
A mesh can require multiples textures. There are all marked with the prefix T_.
To define the type/role of each texture, we commonly use the following suffixes:
  • _Albedo or _BC for the base color.
  • _N for normal maps.
  • _ORM for packed oclussion, roughness and metallic textures
  • ...
